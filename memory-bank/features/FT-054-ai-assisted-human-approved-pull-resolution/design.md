## Context

The feature adds a public CLI plan/apply contract at the boundary between a human reviewer, an optional AI proposal, the local downstream payload, its ownership lock and a pinned source. `brief.md` requires exact review identity and atomic application; current ownership planning and transaction code provide the local baseline.

### C4 Artifact

| Element | Interaction / boundary |
| --- | --- |
| Human reviewer | Reviews an agent-prepared plan and records every ambiguous adapted action. |
| AI agent / UI | Reads plan/context and may write a candidate plan or merge bytes; has no approval channel. |
| `memory-bank-cli pull` | Emits a read-only JSON plan; validates a reviewed plan and atomically applies deterministic bytes. |
| Downstream payload + `memory-bank/.lock` | Local state to be identity-checked and committed together. |
| Pinned template source | Upstream payload and immutable source identity to be identity-checked. |

## Selected Solution

- `SOL-01` Add a versioned JSON resolution-plan representation generated by a non-mutating `pull` planning mode. It records plan schema/version, pinned source identity, lock identity, and per-path ownership, base/local/upstream identities, proposed safe action, reason, allowed actions, decision state, and—when relevant—exact reviewed result bytes/digest and mode.
- `SOL-02` Apply mode parses strictly, rejects unknown schema/action/path data, recomputes each recorded identity against current lock, source and local state, rejects unresolved two-sided adapted paths, and derives final ownership changes only from valid accepted actions.
- `SOL-03` Once validation succeeds, reuse the ownership transaction boundary to stage payload and `.lock` together. Default `pull` remains its existing conservative behavior; plan/apply is opt-in and does not contact an LLM.

## Alternatives Considered

| Alternative ID | Option | Why not selected |
| --- | --- | --- |
| `ALT-01` | Let an AI or plan generator choose adapted actions. | Violates `REQ-04` and `CON-02`; a proposal is not human approval. |
| `ALT-02` | Re-run current planning and apply only path/action names. | Does not bind review to source, lock or exact payload/merge bytes and cannot detect all stale review inputs. |
| `ALT-03` | Retain terminal-only `--ask`. | Cannot be committed, reviewed asynchronously, or prepared by an agent. |

## Trade-offs

| Trade-off ID | Decision | Benefit | Cost / Risk |
| --- | --- | --- | --- |
| `TRD-01` | Require plan completeness and identity revalidation before every apply. | Prevents stale/tampered or partly approved updates. | Plan may need regeneration after any relevant change. |
| `TRD-02` | Store reviewed merge result rather than recomputing it at apply time. | Human reviews the exact bytes/mode the CLI writes. | Larger plan files and strict codec validation. |

## Accepted Local Decisions

- `SD-01` JSON is the feature-local plan serialization because existing CLI reports and locks already use JSON; schema versioning and strict decoding make the review carrier deterministic.
- `SD-02` `keep-and-detach` is represented as a deterministic safe action only for the issue-defined missing-template user-owned case; it never licenses deletion of user-owned content.

## Contracts

| Contract ID | Connector / direction | Roles and sync boundary | Guarantees / failure / evolution semantics |
| --- | --- | --- | --- |
| `CTR-01` | Versioned JSON plan: CLI/agent -> reviewer -> CLI | Writer may be CLI or agent; reviewer authorizes; apply is synchronous local read. | Strict schema and path validation; records digests, modes and source/lock identity; unknown/tampered/stale fields fail before mutation; schema version supports explicit evolution. |
| `CTR-02` | Local source/lock/payload reads -> ownership transaction | CLI is deterministic executor; no external AI provider. | Validate all identities and completed decisions before transaction; no retry or partial degradation; transaction commits payload and lock together or leaves both unchanged. |

## Invariants

- `INV-01` Plan generation and every rejected apply leave downstream payload and `.lock` unchanged.
- `INV-02` Apply may mutate only when each plan-bound source, lock, local and upstream identity still matches the reviewed plan.
- `INV-03` No unresolved two-sided adapted path, AI inference, or unbound merge result can authorize mutation.
- `INV-04` File content and executable mode are part of the result reviewed and applied for any action that replaces or merges a file.

## Failure Modes

- `FM-01` Schema, action, path or digest tampering is rejected during strict parse/validation before staging.
- `FM-02` Any stale lock/source/local/template payload is rejected before staging; reviewer regenerates and re-reviews a plan.
- `FM-03` A staging or commit failure invokes the existing transaction rollback, leaving payload and lock unchanged.
