## Context

The feature adds a public CLI plan/apply contract at the boundary between a human reviewer, an optional AI proposal, the local downstream payload, its ownership lock and a pinned source. `brief.md` requires exact review identity and atomic application; current ownership planning and transaction code provide the local baseline.

### C4 Artifact

| Element | Interaction / boundary |
| --- | --- |
| Human reviewer | Reviews the canonical plan digest and records every ambiguous adapted action by creating a detached approval attestation with an authorized human-controlled signing key. |
| AI agent / UI | Reads plan/context and may write a candidate plan; has no approval channel or access to an authorized signing key. |

| Pinned template source | Upstream payload and immutable source identity to be identity-checked. |

## Selected Solution

- `SOL-01` Add a versioned JSON resolution-plan representation generated by a non-mutating `pull` planning mode. Its canonical serialization records plan schema/version, pinned source identity, lock identity, and per-path ownership, base/local/upstream identities, proposed safe action, reason, allowed actions and decision state. The canonical whole-plan digest covers every action and result field.
- `SOL-02` Apply accepts a plan only with a detached approval attestation over its canonical whole-plan digest. The attestation is verified against the configured authorized human-reviewer public-key policy; the signing key is outside the agent/plan-writer authority. The CLI recomputes the digest and rejects a missing, invalid, unauthorized or mismatched attestation before staging.
- `SOL-03` For a proposed non-overlapping mechanical merge, planning records canonical base bytes whose digest must equal the recorded lock base identity, plus the local and upstream bytes/identities, merge algorithm version and result bytes/digest/mode. The CLI performs that specified deterministic three-way merge during planning, rejects an overlapping change, and recomputes it during apply; apply accepts the action only when its recomputed result and mode equal the reviewed, attested fields. Other explicit human actions may select the validated local or upstream bytes, but cannot label arbitrary bytes as a mechanical merge.
- `SOL-04` Apply mode parses strictly, rejects unknown schema/action/path data, verifies the approval attestation, recomputes each recorded identity against current lock, source and local state, rejects unresolved two-sided adapted paths, and derives final ownership changes only from valid accepted actions. Once validation succeeds, reuse the ownership transaction boundary to stage payload and `.lock` together. Default `pull` remains its existing conservative behavior; plan/apply is opt-in and does not contact an LLM.

## Alternatives Considered

| Alternative ID | Option | Why not selected |
| --- | --- | --- |
| `ALT-01` | Let an AI or plan generator choose adapted actions. | Violates `REQ-04` and `CON-02`; a proposal is not human approval. |
| `ALT-02` | Re-run current planning and apply only path/action names. | Does not bind review to source, lock or exact payload/merge bytes and cannot detect all stale review inputs. |
| `ALT-03` | Retain terminal-only `--ask`. | Cannot be committed, reviewed asynchronously, or prepared by an agent. |

## Trade-offs

| Trade-off ID | Decision | Benefit | Cost / Risk |
| --- | --- | --- | --- |
| `TRD-01` | Require plan completeness, detached human approval and identity revalidation before every apply. | Prevents an agent-authored plan, stale inputs or a partly approved update from authorizing mutation. | Reviewers need an authorized signing key; a plan may need regeneration and re-approval after any relevant change. |
| `TRD-02` | Store and recompute the reviewed mechanical-merge result. | Human reviews the exact bytes/mode the CLI writes and the CLI proves they are the specified non-overlapping mechanical merge. | Larger plan files and a versioned deterministic merge implementation. |

## Accepted Local Decisions

- `SD-01` JSON is the feature-local plan serialization because existing CLI reports and locks already use JSON; schema versioning and strict decoding make the review carrier deterministic.
- `SD-02` `keep-and-detach` is represented as a deterministic safe action only for the issue-defined missing-template user-owned case; it never licenses deletion of user-owned content.
- `SD-03` A detached approval attestation is the approval carrier. It signs the canonical plan digest and is verified against an authorized human-reviewer public key, so changing an agent-writable plan cannot create or transfer approval.

## Contracts

| Contract ID | Connector / direction | Roles and sync boundary | Guarantees / failure / evolution semantics |
| --- | --- | --- | --- |
| `CTR-01` | Versioned JSON plan plus detached attestation: CLI/agent -> reviewer -> CLI | Writer may be CLI or agent; reviewer authorizes only by a configured human-controlled signing key; apply synchronously reads both carriers. | Strict schema/path validation and canonical digest; attestation covers every plan field. Unknown, unsigned, unauthorized, tampered or stale data fails before mutation; schema/merge-algorithm versions support explicit evolution. |
| `CTR-02` | Local source/lock/payload reads -> ownership transaction | CLI is deterministic executor; no external AI provider. | Validate all identities, completed decisions and mechanical-merge recomputation before transaction; no retry or partial degradation; transaction commits payload and lock together or leaves both unchanged. |

## Invariants

- `INV-01` Plan generation and every rejected apply leave downstream payload and `.lock` unchanged.
- `INV-02` Apply may mutate only when a valid authorized human attestation covers the exact canonical plan digest and each plan-bound source, lock, local and upstream identity still matches that attested plan.
- `INV-03` No unresolved two-sided adapted path, AI inference, unsigned plan change or result not reproduced by the specified mechanical merge can authorize mutation.
- `INV-04` File content and executable mode are part of the result reviewed and applied for any action that replaces or merges a file.
- `INV-05` A plan is applicable only to its recorded pre-state. After a successful apply changes a bound identity, replaying that plan is stale and must be rejected; determinism is demonstrated by applying the same attested plan to separate identical pre-state fixtures.

## Failure Modes

- `FM-01` Schema, action, path or digest tampering, or a missing/invalid/unauthorized approval attestation, is rejected during strict parse/validation before staging.
- `FM-02` Any stale lock/source/local/template payload is rejected before staging; reviewer regenerates and re-reviews a plan.
- `FM-03` A staging or commit failure invokes the existing transaction rollback, leaving payload and lock unchanged.
