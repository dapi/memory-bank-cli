## Context

The feature adds a public CLI plan/apply contract at the boundary between a human reviewer, an optional AI proposal, the local downstream payload, its ownership lock and a pinned source. `brief.md` requires exact review identity and atomic application; current ownership planning and transaction code provide the local baseline.

## Selected Solution

- `SOL-01` Add a versioned JSON resolution-plan representation generated by a non-mutating `pull` planning mode. Its canonical serialization records plan schema/version, implicit-full or explicit path scope selector, pinned source identity, lock identity, and per-path ownership, base/local/upstream identities, proposed safe action, reason, allowed actions and decision state. Every field except an explicit scope selector, the selected action, the decision state mechanically derived from that action, and separate human-authorization material is a deterministic CLI-derived proposal field: the schema permits no agent-authored commentary, and `reason` is a canonical reason code with schema-defined parameters/rendering. The implicit full-scope selector is deterministic; an explicit selector is a requester-chosen, authorization-covered scope overlay that the CLI validates against its recomputed affected-path set. A path with `decision-state` `unresolved` has a nullable selected action with the value `null`; a resolved path has one selected executable action. `allowed-actions` contains only actions currently selectable for that path; an enum action absent from that list is unavailable, and the reason records why when relevant. A bounded plan additionally records a complete deterministic affected-path decision inventory, ordered by canonical path, with every path's classification, proposed/allowed action and human-decision requirement; its action list may contain only the selected subset, but the inventory exposes every omitted decision. The canonical whole-plan digest covers the scope selector, complete decision inventory, every action and every result field.
- `SOL-02` Apply accepts a plan only with independently verifiable, tamper-resistant human authorization over its canonical whole-plan digest. `BD-01` must select and approve the human-authorization carrier and verification format, canonicalization procedure, trust policy/configuration, credential lifecycle and reviewer authorization workflow before this mechanism is implemented or the package is called Plan Ready. The selected mechanism must keep approval authority outside the agent/plan-writer authority and cause the CLI to reject missing, invalid, unauthorized or mismatched authorization before staging.
- `SOL-03` A non-overlapping mechanical merge is available only when the base bytes are recoverable from authoritative historical-base state retained with the ownership lock. To preserve rollback compatibility, the existing `.lock` wire format remains unchanged: a versioned `memory-bank/.lock-history-v1` sidecar is the sole authority for each retained historical-base record's presence (`present` or `absent`) and for optional snapshot availability. A retained current-bound base descriptor is independent of optional snapshot bytes: it preserves the verified base presence, identity and executable mode needed for ownership planning even when a present base's bytes cannot be retained. An absent descriptor is a tombstone with no bytes or executable mode. A missing descriptor means historical-base state is unavailable, not that the corresponding valid `.lock` entry is invalid; it cannot enable a mechanical merge, but the existing lock ownership information remains usable for non-merge ownership transitions. A tombstone never replaces or extends a `.lock` entry: its `adapted` or `managed` entry retains the strict wire format's required digest and mode, copied from that entry's last present upstream base. New binaries must not interpret those legacy fields as a current base when the bound descriptor says `absent`; they may use the descriptor's present identity when its snapshot is unavailable for merge. Older binaries may continue their existing behavior from the legacy fields. For each newly established or accepted present upstream base, the ownership transaction applies `SOL-05`'s deterministic descriptor allocation and atomically writes a retained current-bound descriptor with its path and post-transaction lock-identity binding, or leaves that present historical-base record unavailable when allocation has no capacity. Every accepted action that establishes an absent upstream base instead atomically writes its verified tombstone descriptor; it is not accepted when `SOL-05` cannot reserve that descriptor. Separately, `SOL-05` allocates optional canonical bytes for a retained present base; an over-quota snapshot is marked unavailable without dropping its retained descriptor, while an accepted absent-base transition always retains its tombstone regardless of byte-snapshot allocation. Removing an ownership entry also removes its sidecar descriptor and any snapshot in that same transaction. `memory-bank/.lock-history-v1` is a reserved control path, excluded from the template/downstream payload trees, affected-path computation and scope selectors. Before any mutation, an existing downstream user file, template payload file, malformed sidecar, or planned payload action at that path is a collision and rejects without mutation. A strictly well-formed sidecar whose global lock binding is stale is authoritative only as unavailable for merge and must not be used to validate records against current lock membership. It may be replaced only by an implicit-full-scope validated clean-baseline/update: planning must independently recompute the complete affected set and every action must be a deterministic, non-merge clean action that establishes or removes a current upstream base without consulting sidecar historical state. Any bounded scope, unresolved/human-selected action, mechanical merge, or other stale-sidecar apply rejects before staging. The eligible transaction discards the entire stale sidecar, including every descriptor and snapshot, and derives a new sparse sidecar solely from its post-state actions under `SOL-05`; it never retains, rebinds or infers any stale record. Current lock entries unrelated to those post-state actions receive no recovered descriptor and remain historical-state unavailable. The pre-transaction lock identity is the identity of the exact `.lock` serialization validated before staging; it is used only to validate the plan and existing sidecar. The post-transaction lock identity is the identity of the exact complete `.lock` serialization staged for commit, after every accepted ownership change and deterministic allocation has been derived. Every newly written sidecar global binding and every newly written or retained sidecar-record binding must equal that post-transaction identity; the transaction commits those exact lock and sidecar serializations together. Until an eligible transaction commits, no mutation or automatic reset occurs. FT-054 performs no implicit overwrite, relocation or migration of a colliding file; an explicit separate migration must resolve a collision first. Planning verifies a current-bound sidecar state against the current lock before recording it in a plan. It must never reconstruct merge bytes from a digest, a plan-supplied value, or an unverified source checkout. For a proposed merge, planning records those verified base bytes, the local and upstream bytes/identities, the `mbc-diff3-lines-v1` algorithm identifier and the result bytes/digest/mode. The CLI runs that algorithm during planning and recomputes it during apply; apply accepts the action only when its result and mode equal the reviewed, human-authorized fields. A legacy lock, missing sidecar, stale sidecar, missing base descriptor, or descriptor whose present snapshot is unavailable marks `apply-reviewed-merge` unavailable; a retained descriptor remains the recorded base for non-merge ownership transitions. A later clean baseline/update may establish retained historical-base state atomically; a digest alone cannot backfill a missing descriptor. Older binaries ignore the sidecar and continue to read the unchanged `.lock`; when a later new binary finds that an older write has changed the lock binding, it treats the sidecar as unavailable for merge and can re-establish it only through the eligible atomic clean-baseline/update transition in this solution.

  **Sidecar freshness, provenance and recovery clarification.** A lock-identity match alone is never sufficient to make a sidecar authoritative: a present descriptor and a later tombstone can intentionally share the same legacy `.lock` serialization. Every sidecar therefore has a fresh, non-reusable generation identifier and a canonical sidecar digest covering its schema, generation, global lock binding, every descriptor and every snapshot-availability/value field. The CLI maintains, outside the payload tree and outside agent/plan-writer filesystem authority, a per-downstream protected history registry. Its monotonic, non-rollbackable receipt binds the canonical downstream root, generation, sidecar digest and current exact lock identity and is authenticated by a device credential unavailable to the plan writer. Planning and apply may treat a sidecar or any descriptor as authoritative only when its receipt independently verifies and exactly matches all four values; a missing, invalid, superseded or mismatched receipt makes all historical state unavailable for merge and record validation. Replaying a previously well-formed sidecar, including one with a repeated lock identity, therefore fails the current-generation receipt check. Registry preparation may precede the payload/lock transaction and receipt finalization follows its commit; a crash or failure that leaves either phase incomplete yields unavailable historical state, never authoritative state, until recovery.

  First adoption is explicit and collision-safe: it may initialize a registry entry and sidecar only during a validated full-scope transaction after observing both no registry receipt and no object at the reserved sidecar path. Any pre-existing object at that path, including a syntactically well-formed current-lock-bound payload, is user content and rejects without mutation; it cannot be adopted, consumed, overwritten or relocated implicitly. A registry receipt without its matching sidecar, or vice versa, is unavailable/corrupt control state and follows the same no-merge recovery path. This procedure establishes durable CLI provenance for every subsequently readable sidecar without changing the `.lock` wire format.

  The preceding stale-sidecar eligibility language is superseded as follows. A stale or receipt-unverifiable sidecar may be discarded only by an implicit-full-scope recovery plan that recomputes the complete affected set without consulting historical records. Every scoped path must be resolved, but may use either a deterministic non-merge action or a separately human-authorized allowed non-merge action such as `keep-local` or `take-upstream`; only `apply-reviewed-merge`, bounded scope and unresolved actions are prohibited. The recovery transaction discards all stale descriptors and snapshots, derives a new generation and sparse sidecar solely from its trusted post-state actions under `SOL-05`, and finalizes the matching registry receipt only after the lock/payload/sidecar transaction commits. It never retains, rebinds or infers stale records; unrelated current lock entries receive no recovered descriptor and remain historical-state unavailable.
- `SOL-04` Apply mode parses strictly, rejects unknown schema/action/path data, verifies human authorization, and derives final ownership changes only from valid accepted actions. A plan has either the deterministic implicit full scope or an explicit scope selector: a sorted, unique, non-empty list of normalized payload paths. Planning first recomputes the full affected-path set, excluding the `SOL-03` reserved control path; an explicit selector is valid only when every selected path is in that set, and the plan records exactly one action for each selected path. The implicit full scope selects the whole set. Apply acquires an exclusive update guard covering the downstream payload, source checkout, ownership lock and lock-history sidecar, then recomputes the full affected-path set and every recorded identity against current lock, source and local state immediately before staging. It regenerates the complete deterministic proposal projection and requires byte-for-byte equality with every deterministic proposal field: path membership/order, ownership and present/absent state labels, identities, proposed action, allowed actions, canonical reason/context, merge eligibility, inputs and result, and the implicit-full selector when used. For explicit scope, it also regenerates and exactly compares the complete affected-path decision inventory; that inventory is authorization-covered and must expose every selected and omitted path's classification, proposed/allowed action and human-decision requirement. An explicit scope selector, the selected action, its mechanically derived decision state, and separately verified human-authorization material are authorization-covered overlays; apply validates each overlay against that regenerated projection. In particular, it validates the selector's normalization, order, uniqueness and membership in the recomputed full affected-path set rather than attempting to regenerate the requester-chosen subset. Any mismatch rejects before staging. It derives the scoped affected-path set by applying the recorded selector and requires it to equal the plan action-path set exactly; an omitted path, duplicate action, extra action, selector that no longer selects an affected path, or scope mismatch rejects before staging. An explicit scope therefore permits an independently reviewable bounded subset when a full plan is too large, without concealing its omitted decisions; unselected affected paths are neither written nor have their lock entries changed. It holds that guard through transaction commit. The guard serializes only writers that participate in it; a non-cooperating writer is outside this mutual-exclusion guarantee, though any change observed by final revalidation rejects the apply before staging. It rejects unresolved two-sided adapted paths within the scoped affected-path set; the ownership transaction stages payload, `.lock` and `.lock-history-v1` together. Default `pull` remains its existing conservative behavior; plan/apply is opt-in and does not contact an LLM.
- `SOL-05` Historical-base and plan payloads are deliberately bounded. The `.lock-history-v1` sidecar is a sparse, bounded cache of historical-base records, not a required mirror of every `.lock` entry: retain at most 4,096 descriptors and at most one optional historical-base byte snapshot per retained descriptor, replacing the prior snapshot atomically. A byte snapshot may contain at most 1 MiB and all retained byte snapshots for a lock may contain at most 64 MiB. A retained current-bound base descriptor is not a byte snapshot and remains retained when that optional snapshot is unavailable. For every ownership transaction that establishes an upstream base, determine descriptor retention from the complete post-transaction candidate set before writing: remove deleted entries; reserve unchanged retained descriptors; release the superseded descriptor and snapshot for every entry receiving a new base; then consider those changed entries in lexicographic normalized payload-path order. Retain a present candidate descriptor only when it fits the 4,096-descriptor and non-snapshot metadata reservations; otherwise leave its historical-base record unavailable. An absent upstream-base candidate is a zero-byte verified tombstone descriptor and must also fit those reservations: planning must not emit, and apply must reject before staging, any selected action that would establish that absent base without a retained tombstone. A retained present candidate is then retained with a byte snapshot only if it is at most 1 MiB and fits the remaining 64 MiB reservation; otherwise its descriptor records a present base with an unavailable snapshot. There is no eviction of an unchanged or already allocated candidate. This rule also governs replacement, so identical pre-state fixtures and actions produce the same retained set. Present-descriptor or optional-snapshot capacity never rejects or disables an otherwise permitted non-merge action: an unretained present descriptor or unavailable snapshot only makes `apply-reviewed-merge` unavailable; tombstone descriptor capacity rejects the absent-base transition rather than dropping its authoritative state.

  Before decoding an existing `.lock-history-v1` sidecar, planning and apply read it through a 96 MiB raw-carrier limit and reject an oversized carrier without first buffering or decoding it. Strict streaming decode permits only the versioned schema's root and descriptor members, at most 4,096 unique normalized-path descriptors, eight nesting levels, 4,096-byte normalized paths and per-descriptor metadata strings, and 512-byte lock-identity and digest fields; duplicate or unknown members and duplicate paths are rejected. All non-snapshot string metadata across the carrier, including paths, identities, digests and state/mode fields, may total at most 4 MiB. After its global lock binding has been verified current, each descriptor must bind to exactly one current lock entry; a current lock entry without a descriptor is valid but has unavailable historical-base state. A structurally valid sidecar with a stale global binding bypasses that record-to-current-lock validation and follows `SOL-03`'s unavailable/recovery path. Descriptor allocation follows the first paragraph's remove/reserve/release/lexicographic-retain rule, including the descriptor-count and metadata reservations, before optional byte-snapshot allocation. An entry whose descriptor or optional snapshot cannot be retained omits `apply-reviewed-merge` from its allowed actions while deterministic and explicitly human-selected non-merge actions remain available. Thus deeply nested values or oversized path/identity metadata are rejected before they can consume unbounded memory or establish state.

  Before decoding, apply obtains the serialized JSON plan through a 16 MiB raw-carrier limit and rejects it when the carrier exceeds that limit; it must not first read or decode an unbounded carrier. Strict streaming decode permits at most 4,096 actions, 4,096 scope paths and 4,096 complete-decision-inventory records, eight nesting levels, 4,096-byte normalized paths and reason/metadata strings, and 512-byte identity strings; arrays and objects have only schema-defined members, duplicate keys and unknown members are rejected. A full-scope plan's action paths and an explicit-scope plan's decision-inventory paths must each exactly equal the recomputed full affected-path set, in canonical order. The complete executable-action enum is `keep-local`, `take-upstream`, `apply-reviewed-merge` and `keep-and-detach`. A selected action is either an executable enum value or `null`: `null` is permitted only with `decision-state` `unresolved`, while every resolved selected action and every allowed-action value must be in that enum and a resolved selected action must be in its path's allowed-action list. Apply rejects an unresolved action until an authorized selection replaces `null`. An allowed-action list has no duplicates and contains at most three values. For a two-sided `adapted` path, the allowed-action set is `keep-local` and `take-upstream`, plus `apply-reviewed-merge` only when the base, local and upstream inputs are all present, a verified present historical base exists, and `mbc-diff3-lines-v1` is eligible under all byte, line, collision, mode and aggregate-work limits; its omission means that merge is unavailable. `keep-and-detach` is valid only for the deterministic missing-template `user-owned` case. These limits count UTF-8 bytes in the serialized values. A plan may inline at most 8 MiB of **decoded** bytes across all base, local, upstream and result byte fields, and no individual decoded field may exceed 1 MiB; their encoded representation counts only toward the 16 MiB carrier limit. A mechanical-merge candidate may contain at most 2,000 lines in each input. Across all mechanical-merge candidates in one plan, the summed LCS work units `base_lines * local_lines + base_lines * upstream_lines` may not exceed 64,000,000. Planning considers candidates in lexicographic payload-path order and checks their line-derived work units before running either LCS; a candidate that would exceed the aggregate budget omits `apply-reviewed-merge` from `allowed-actions` and records it as unavailable in the reason, while permitted non-merge actions remain available. Apply recomputes the same work units for every selected mechanical merge and rejects an over-budget plan before running LCS or staging. Hashing and quota accounting stream file bytes; the merge implementation may materialize only inputs that have passed these byte, line and aggregate-work limits. If a present-base snapshot cannot be retained within the snapshot quotas, its retained descriptor records that snapshot as unavailable while preserving the present base identity; the path omits `apply-reviewed-merge` from `allowed-actions`, while deterministic and explicitly human-selected non-merge actions remain available. If planning exceeds a plan quota, it rejects without mutation; the requester may generate an explicit-scope plan for a selected subset, whose complete decision inventory and exact scoped affected-path coverage are then enforced by `SOL-04`. These limits are schema-versioned contract values, not advisory defaults.

### Canonical payload paths and filesystem resolution

Every payload path in a plan, lock-history record, scope selector, affected-path set, digest input or deterministic-allocation calculation is the same canonical logical path. Its JSON string is valid UTF-8 and Unicode NFC; it is one or more non-empty segments joined by the literal ASCII `/`, with no leading or trailing `/`, repeated `/`, `.` or `..` segment, NUL, backslash, or ASCII control character. The supplied string must already equal this form; decoding, separator conversion, dot-component collapse, percent decoding, case folding, Unicode normalization, or symlink resolution must never turn a non-canonical spelling into an accepted path. `memory-bank/.lock-history-v1` is compared as this canonical logical path before every payload/control-path collision and is therefore excluded even when it appears through a non-canonical spelling, which is rejected rather than normalized.

The canonical ordering is lexicographic order of the canonical UTF-8 byte sequences, comparing each byte as an unsigned value `0` through `255`; a shorter sequence sorts before a longer sequence when it is its byte prefix. This order is used without locale collation for action paths, selectors, sidecar records and all `SOL-05` allocation decisions.

Planning and apply resolve a canonical payload path only by a component-by-component, no-follow walk from the configured payload root. The root and every existing traversed component must be a real directory entry, and no traversed component may be a symlink. The leaf, when present, must be a real entry of the expected type and not a symlink. For an expected absent local or upstream state, the walk may terminate at the first `ENOENT` component, including an ancestor, and records the complete canonical path as absent; no component after that absence is traversed. A symlink, filesystem alias or every other traversal failure among existing components is rejected.

  Filesystem spelling is handled portably rather than by excluding a filesystem class. For each payload root, planning builds the no-follow logical directory view from enumerated entry names: valid UTF-8 entry names are NFC-canonicalized only for that view, and any two entries in one directory that map to the same canonical logical name are an alias collision. A requested component must select its exact canonical logical name in that view. If a differently cased, normalized, or otherwise aliased spelling resolves through the filesystem to an existing entry, it is an alias collision rather than an absent path. Planning and apply reject only the affected payload/control-path operation on an alias collision, before mutation; non-colliding paths remain eligible. This preserves one-to-one canonical-path identity and reserved-control-path protection on case-insensitive or Unicode-normalizing filesystems without assigning an implementation-specific spelling.

### Mechanical-merge algorithm: `mbc-diff3-lines-v1`

`mbc-diff3-lines-v1` is the normative algorithm for `apply-reviewed-merge`; no platform `diff3` binary, library default or implementation-specific heuristic is part of the contract. It operates only on regular, NUL-free files. If any of the verified base, local or upstream byte streams contains a NUL byte, mechanical merge is unavailable. It treats each byte stream as complete lines ending in LF, preserving every byte in each line (including a preceding CR); a final unterminated byte sequence is one final line. It performs no character decoding, line-ending normalization or whitespace normalization.

For each side, derive base-to-side edit hunks from a longest common subsequence of those line sequences. When multiple longest common subsequences exist, select the one whose ordered sequence of `(base-line-index, side-line-index)` pairs is lexicographically smallest. A hunk replaces one contiguous half-open base-line interval with its side's replacement lines. The merge is unavailable when the two hunk sets collide: two non-empty base intervals intersect, two insertions use the same base boundary, or an insertion is strictly inside another hunk's non-empty base interval. Otherwise, emit the base lines in order: after a non-empty hunk ends, emit an insertion at that boundary, then begin a non-empty hunk at that boundary. The result is encoded by concatenating those preserved lines exactly.

The result mode is: the common local/upstream mode when they are equal; otherwise the changed side's mode when the other side equals the base mode. If both sides differ from the base mode and from each other, mechanical merge is unavailable as a mode conflict. Thus binary input, a content collision or a mode conflict has no merge result to encode, and apply rejects any plan that nevertheless selects `apply-reviewed-merge`.

### Adapted state/action contract

`absent` is a first-class sidecar tombstone state, not an empty file: it has no bytes and no executable mode. The sidecar is authoritative for that state; the corresponding `.lock` entry remains a strict legacy-format `adapted` or `managed` entry carrying the last present upstream digest and mode, not an absent-base representation. In the first table, `changed, present` means a present file whose identity differs from the present recorded base, and `unchanged, present` means it equals that base. Its original recorded base is present; an accepted current-absent upstream transition atomically retains a verified tombstone descriptor for the next baseline, and is rejected before staging if `SOL-05` cannot reserve it. The second table defines the next-pull transitions when that recorded base is the tombstone.

### Deterministic safe state/action contract

| Recorded ownership and state | Action | Payload after apply | Ownership / `.lock` after apply | Human decision |
| --- | --- | --- | --- | --- |
| `managed`; local equals recorded base and upstream has changed | `take-upstream` | Write the recorded upstream bytes and executable mode. | Retain `managed`; atomically replace the path's lock entry with the resulting upstream identity and mode. | Not required; deterministic safe action. |
| `managed`; local equals present recorded base and upstream is absent | `take-upstream` | Delete the local path; no bytes or executable mode are written. | Retain `managed` and its valid legacy `.lock` digest/mode; atomically retain the verified absent upstream-base tombstone descriptor. | Not required; deterministic safe action; reject before staging if tombstone capacity cannot be reserved. |
| `user-owned`; path is absent from the current template | `keep-and-detach` | Preserve the existing local bytes and executable mode exactly; no deletion or rewrite. | Remove the path's ownership entry from `.lock` and its sidecar record; commit both updates atomically with the unchanged payload. | Not required; deterministic safe action. |

## Alternatives Considered

| Alternative ID | Option | Why not selected |
| --- | --- | --- |
| `ALT-01` | Let an AI or plan generator choose adapted actions. | Violates `REQ-04` and `CON-02`; a proposal is not human approval. |
| `ALT-02` | Re-run current planning and apply only path/action names. | Does not bind review to source, lock or exact payload/merge bytes and cannot detect all stale review inputs. |
| `ALT-03` | Retain terminal-only `--ask`. | Cannot be committed, reviewed asynchronously, or prepared by an agent. |

## Trade-offs

| Trade-off ID | Decision | Benefit | Cost / Risk |
| --- | --- | --- | --- |
| `TRD-01` | Require plan completeness, independently verifiable human authorization and identity revalidation before every apply. | Prevents an agent-authored plan, stale inputs or a partly approved update from authorizing mutation. | Reviewers must use the `BD-01`-approved workflow; a plan may need regeneration and re-approval after any relevant change. |
| `TRD-02` | Store and recompute the reviewed mechanical-merge result. | Human reviews the exact bytes/mode the CLI writes and the CLI proves they are the specified non-overlapping mechanical merge. | Larger plan files and a versioned deterministic merge implementation. |

## Accepted Local Decisions

- `SD-01` JSON is the feature-local plan serialization because existing CLI reports and locks already use JSON; schema versioning and strict decoding make the review carrier deterministic.
- `SD-02` `keep-and-detach` is a member of the strict action enum, but is represented as a deterministic safe action only for the issue-defined missing-template user-owned case. Before apply, the path is `user-owned`, has a lock entry, and is absent from the current template; apply preserves its exact bytes and executable mode, removes its ownership entry from `.lock` and its lock-history sidecar record, and atomically commits the unchanged payload with those state changes. It never licenses deletion or rewrite of user-owned content.
- `SD-03` **Blocked by `BD-01`.** The concrete approval carrier and verification format, canonicalization procedure, trust policy/configuration, credential lifecycle and reviewer authorization workflow require explicit human approval. Whichever mechanism is selected must satisfy `SOL-02` without granting an agent/plan writer approval authority.

## Invariants

- `INV-01` Plan generation and every rejected apply leave downstream payload and `.lock` unchanged.
- `INV-02` Apply may mutate only when valid human authorization covers the exact canonical plan digest and, while holding the exclusive update guard, the independently regenerated deterministic proposal projection exactly matches every deterministic plan field. An explicit scope must contain a complete authorization-covered decision inventory exactly matching the recomputed full affected-path set; its selector is validated as normalized, sorted, unique, non-empty and wholly contained in that set, and the recomputed scoped affected-path set has exactly one valid plan action per path and no extra actions. Each plan-bound source, lock, local and upstream identity still matches that authorized plan. The scoped set is the complete full affected-path set for an implicit scope, or exactly the declared valid explicit selector.
- `INV-03` No unresolved or omitted two-sided adapted path within the authorized scoped affected-path set, AI inference, unauthorized plan change or result not reproduced by the specified mechanical merge can authorize mutation. Paths outside a valid explicit scope are not omissions and remain unchanged.
- `INV-04` File content and executable mode are part of the result reviewed and applied for any action that replaces or merges a file.
- `INV-05` A plan is applicable only to its recorded pre-state. After a successful apply changes a bound identity, replaying that plan is stale and must be rejected; a successful no-op plan whose bound identities remain unchanged may be applied again idempotently. Determinism is demonstrated by applying the same human-authorized plan to separate identical pre-state fixtures.
- `INV-06` A cooperating writer cannot modify the guarded payload, source checkout or ownership lock between final identity validation and the transaction commit. Non-cooperating processes are not covered by this invariant.
- `INV-07` A mechanical merge never uses a reconstructed or plan-supplied historical base: its bytes and mode must be recovered from, and verified against, the lock-bound `.lock-history-v1` snapshot. That sidecar is authoritative for absent and unavailable base state only when its fresh generation and canonical digest exactly match the independently verified protected receipt; a legacy `.lock` entry's retained required digest/mode must not substitute for it. A legacy entry, missing sidecar, stale sidecar binding, missing receipt or replayed/mismatched receipt cannot select `apply-reviewed-merge`.
- `INV-08` Retained historical-base and inlined plan bytes, the bounded sidecar and serialized-plan carriers, their structural and aggregate metadata, and aggregate mechanical-merge LCS work never exceed the `SOL-05` quotas. Any malformed-carrier, structural or plan quota rejection leaves payload, lock and sidecar unchanged. Descriptor and optional-snapshot allocation uses only the `SOL-05` sorted reservation rules: when an accepted action moves to a present candidate that does not fit descriptor capacity, its payload and unchanged-format lock commit with that present historical-base record unavailable; when its descriptor fits but its present snapshot does not, the sidecar records that snapshot as unavailable. An action establishing an absent base is never accepted without its tombstone: insufficient tombstone descriptor capacity rejects before staging and leaves payload, lock and sidecar unchanged.

## Failure Modes

- `FM-01` An oversized raw plan or lock-history-sidecar carrier is rejected before decoding; schema, duplicate/unknown/oversized field, excessive sidecar record/metadata aggregate, action, path or digest tampering, any non-decision review-context mismatch, or missing/invalid/unauthorized human authorization, is rejected during strict parse/validation before staging.
- `FM-02` Any stale lock/source/local/template payload observed during final validation is rejected before staging; the exclusive update guard prevents a cooperating writer from creating a validation-to-commit race, and the reviewer regenerates and re-reviews a plan. A non-cooperating mutation that is not observable by final validation is outside the serialization contract.
- `FM-03` A staging or commit failure invokes the existing transaction rollback, leaving payload, unchanged-format lock and lock-history sidecar, including any historical-base snapshot, unchanged.
- `FM-04` A present historical-base candidate that does not fit descriptor capacity is recorded as unavailable, while an absent-base candidate that does not fit tombstone descriptor capacity is rejected before staging; a retained descriptor whose present snapshot exceeds its quota is recorded with that snapshot unavailable according to the deterministic reservation order; a mechanical-merge candidate exceeding the aggregate LCS-work budget is recorded as unavailable; and an over-limit sidecar carrier/structure/metadata aggregate, plan carrier, decoded plan, or selected mechanical merge is rejected before staging. Neither condition permits truncation, a dropped tombstone, a reconstructed base or an unreviewed fallback action.
- `FM-05` A missing, invalid, superseded, replayed or mismatched protected history receipt, or an interrupted receipt preparation/finalization, never authenticates a sidecar. Historical state is unavailable; a full-scope plan may recover only through resolved deterministic or human-authorized non-merge actions, while bounded, unresolved and reviewed-merge recovery rejects before staging. A pre-existing would-be sidecar during first adoption is a collision and is never consumed or overwritten.
