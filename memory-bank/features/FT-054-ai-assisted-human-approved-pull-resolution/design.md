## Context

The feature adds a public CLI plan/apply contract at the boundary between a human reviewer, an optional AI proposal, the local downstream payload, its ownership lock and a pinned source. `brief.md` requires exact review identity and atomic application; current ownership planning and transaction code provide the local baseline.

## Selected Solution

- `SOL-01` Add a versioned JSON resolution-plan representation generated by a non-mutating `pull` planning mode. Its canonical serialization records plan schema/version, pinned source identity, lock identity, and per-path ownership, base/local/upstream identities, proposed safe action, reason, allowed actions and decision state. The canonical whole-plan digest covers every action and result field.
- `SOL-02` Apply accepts a plan only with independently verifiable, tamper-resistant human authorization over its canonical whole-plan digest. `BD-01` must select and approve the attestation/signature format, canonicalization procedure, trust-store configuration, key lifecycle and reviewer signing workflow before this mechanism is implemented or the package is called Plan Ready. The selected mechanism must keep its signing authority outside the agent/plan-writer authority and cause the CLI to reject missing, invalid, unauthorized or mismatched authorization before staging.
- `SOL-03` A non-overlapping mechanical merge is available only when the base bytes are recoverable from the authoritative historical-base snapshot retained in a versioned ownership-lock extension. For each newly established or accepted upstream base, the ownership transaction atomically retains the canonical base bytes and executable mode in that lock extension and records its digest, mode and path binding; planning reads that snapshot and verifies it against the lock before recording its bytes in a plan. It must never reconstruct a base from a digest, a plan-supplied value, or an unverified source checkout. For a proposed merge, planning records those verified base bytes, plus the local and upstream bytes/identities, merge algorithm version and result bytes/digest/mode. The CLI performs that specified deterministic three-way merge during planning, rejects an overlapping change, and recomputes it during apply; apply accepts the action only when its recomputed result and mode equal the reviewed, human-authorized fields. A legacy lock entry without a verifiable historical-base snapshot marks `apply-reviewed-merge` unavailable; it may use another permitted human action, but it cannot be mechanically merged. A later clean baseline/update may establish a snapshot atomically; a digest alone cannot backfill one.
- `SOL-04` Apply mode parses strictly, rejects unknown schema/action/path data, verifies human authorization, and derives final ownership changes only from valid accepted actions. It acquires an exclusive update guard covering the downstream payload, source checkout and ownership lock, then recomputes each recorded identity against current lock, source and local state immediately before staging and holds that guard through transaction commit. The guard serializes only writers that participate in it; a non-cooperating writer is outside this mutual-exclusion guarantee, though any change observed by final revalidation rejects the apply before staging. It rejects unresolved two-sided adapted paths; the ownership transaction stages payload and `.lock` together. Default `pull` remains its existing conservative behavior; plan/apply is opt-in and does not contact an LLM.

### Adapted one-sided state/action contract

| Recorded ownership | Local state relative to base | Upstream state relative to base | Action | Result ownership | Result content and mode | Human decision |
| --- | --- | --- | --- | --- | --- | --- |
| `adapted` | changed | unchanged | `keep-local` | `adapted` | Recorded local bytes and executable mode | Not required; deterministic safe action. |
| `adapted` | unchanged | changed | `take-upstream` | `adapted` | Recorded upstream bytes and executable mode | Not required; deterministic safe action. |
| `adapted` | changed | changed | unresolved | unchanged until a permitted action is human-authorized | No payload or mode change during plan/apply rejection | Required: `keep-local`, `take-upstream`, or `apply-reviewed-merge`. |

### Deterministic safe state/action contract

| Recorded ownership and state | Action | Payload after apply | Ownership / `.lock` after apply | Human decision |
| --- | --- | --- | --- | --- |
| `managed`; local equals recorded base and upstream has changed | `take-upstream` | Write the recorded upstream bytes and executable mode. | Retain `managed`; atomically replace the path's lock entry with the resulting upstream identity and mode. | Not required; deterministic safe action. |
| `user-owned`; path is absent from the current template | `keep-and-detach` | Preserve the existing local bytes and executable mode exactly; no deletion or rewrite. | Remove the path's ownership entry from `.lock`; commit that lock update atomically with the unchanged payload. | Not required; deterministic safe action. |

## Alternatives Considered

| Alternative ID | Option | Why not selected |
| --- | --- | --- |
| `ALT-01` | Let an AI or plan generator choose adapted actions. | Violates `REQ-04` and `CON-02`; a proposal is not human approval. |
| `ALT-02` | Re-run current planning and apply only path/action names. | Does not bind review to source, lock or exact payload/merge bytes and cannot detect all stale review inputs. |
| `ALT-03` | Retain terminal-only `--ask`. | Cannot be committed, reviewed asynchronously, or prepared by an agent. |

## Trade-offs

| Trade-off ID | Decision | Benefit | Cost / Risk |
| --- | --- | --- | --- |
| `TRD-01` | Require plan completeness, detached human approval and identity revalidation before every apply. | Prevents an agent-authored plan, stale inputs or a partly approved update from authorizing mutation. | Reviewers need an authorized signing key; a plan may need regeneration and re-approval after any relevant change. |
| `TRD-02` | Store and recompute the reviewed mechanical-merge result. | Human reviews the exact bytes/mode the CLI writes and the CLI proves they are the specified non-overlapping mechanical merge. | Larger plan files and a versioned deterministic merge implementation. |

## Accepted Local Decisions

- `SD-01` JSON is the feature-local plan serialization because existing CLI reports and locks already use JSON; schema versioning and strict decoding make the review carrier deterministic.
- `SD-02` `keep-and-detach` is represented as a deterministic safe action only for the issue-defined missing-template user-owned case. Before apply, the path is `user-owned`, has a lock entry, and is absent from the current template; apply preserves its exact bytes and executable mode, removes its ownership entry from `.lock`, and atomically commits the unchanged payload with that lock change. It never licenses deletion or rewrite of user-owned content.
- `SD-03` **Blocked by `BD-01`.** The concrete approval carrier, canonicalization procedure, trust-store configuration, key lifecycle and reviewer signing workflow require explicit human approval. Whichever mechanism is selected must satisfy `SOL-02` without granting an agent/plan writer approval authority.

## Contracts

| Contract ID | Connector / direction | Roles and sync boundary | Guarantees / failure / evolution semantics |
| --- | --- | --- | --- |
| `CTR-01` | Versioned JSON plan plus selected human-authorization carrier: CLI/agent -> reviewer -> CLI | Writer may be CLI or agent; the reviewer authorizes only through the `BD-01`-approved workflow; apply synchronously reads both carriers. | Strict schema/path validation and canonical digest; selected authorization covers every plan field. Unknown, missing, unauthorized, tampered or stale data fails before mutation; schema/merge-algorithm versions support explicit evolution. |
| `CTR-02` | Local source/lock/payload and lock-retained historical-base snapshot reads -> exclusive update guard -> ownership transaction | CLI is deterministic executor; no external AI provider; all cooperating writers use the same guard. | Acquire the guard, verify a mechanical-merge base snapshot against its lock binding when present, perform final identity validation and completed-decision/mechanical-merge recomputation, then commit payload and lock (including any newly established base snapshot) before release. A missing legacy snapshot makes mechanical merge unavailable rather than guessed. A competing cooperating writer waits or fails without interleaving; transaction commits all bound state together or leaves it unchanged. A non-cooperating writer is not mutually excluded; a mutation observed during final validation rejects before staging, while an unobservable commit-boundary race remains outside this contract. |

## Invariants

- `INV-01` Plan generation and every rejected apply leave downstream payload and `.lock` unchanged.
- `INV-02` Apply may mutate only when valid human authorization covers the exact canonical plan digest and, while holding the exclusive update guard, each plan-bound source, lock, local and upstream identity still matches that authorized plan.
- `INV-03` No unresolved two-sided adapted path, AI inference, unauthorized plan change or result not reproduced by the specified mechanical merge can authorize mutation.
- `INV-04` File content and executable mode are part of the result reviewed and applied for any action that replaces or merges a file.
- `INV-05` A plan is applicable only to its recorded pre-state. After a successful apply changes a bound identity, replaying that plan is stale and must be rejected; determinism is demonstrated by applying the same human-authorized plan to separate identical pre-state fixtures.
- `INV-06` A cooperating writer cannot modify the guarded payload, source checkout or ownership lock between final identity validation and the transaction commit. Non-cooperating processes are not covered by this invariant.
- `INV-07` A mechanical merge never uses a reconstructed or plan-supplied historical base: its bytes and mode must be recovered from, and verified against, the lock-retained historical-base snapshot. A legacy entry without that snapshot cannot select `apply-reviewed-merge`.

## Failure Modes

- `FM-01` Schema, action, path or digest tampering, or missing/invalid/unauthorized human authorization, is rejected during strict parse/validation before staging.
- `FM-02` Any stale lock/source/local/template payload observed during final validation is rejected before staging; the exclusive update guard prevents a cooperating writer from creating a validation-to-commit race, and the reviewer regenerates and re-reviews a plan. A non-cooperating mutation that is not observable by final validation is outside the serialization contract.
- `FM-03` A staging or commit failure invokes the existing transaction rollback, leaving payload and lock, including any historical-base snapshot, unchanged.
