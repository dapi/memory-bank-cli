## Context

The feature adds a public CLI plan/apply contract at the boundary between a human reviewer, an optional AI proposal, the local downstream payload, its ownership lock and a pinned source. `brief.md` requires exact review identity and atomic application; current ownership planning and transaction code provide the local baseline.

## Selected Solution

- `SOL-01` Add a versioned JSON resolution-plan representation generated by a non-mutating `pull` planning mode. Its canonical serialization records plan schema/version, implicit-full or explicit path scope selector, pinned source identity, lock identity, and per-path ownership, base/local/upstream identities, proposed safe action, reason, allowed actions and decision state. Every field except the selected action, the decision state mechanically derived from that action, and separate human-authorization material is a deterministic CLI-derived proposal field: the schema permits no agent-authored commentary, and `reason` is a canonical reason code with schema-defined parameters/rendering. A path with `decision-state` `unresolved` has a nullable selected action with the value `null`; a resolved path has one selected executable action. `allowed-actions` contains only actions currently selectable for that path; an enum action absent from that list is unavailable, and the reason records why when relevant. The canonical whole-plan digest covers the scope selector, every action and every result field.
- `SOL-02` Apply accepts a plan only with independently verifiable, tamper-resistant human authorization over its canonical whole-plan digest. `BD-01` must select and approve the human-authorization carrier and verification format, canonicalization procedure, trust policy/configuration, credential lifecycle and reviewer authorization workflow before this mechanism is implemented or the package is called Plan Ready. The selected mechanism must keep approval authority outside the agent/plan-writer authority and cause the CLI to reject missing, invalid, unauthorized or mismatched authorization before staging.
- `SOL-03` A non-overlapping mechanical merge is available only when the base bytes are recoverable from authoritative historical-base state retained with the ownership lock. To preserve rollback compatibility, the existing `.lock` wire format remains unchanged: a versioned `memory-bank/.lock-history-v1` sidecar is the sole authority for whether historical-base state is retained with present bytes, absent as a tombstone, or unavailable. A tombstone never replaces or extends a `.lock` entry: its `adapted` or `managed` entry retains the strict wire format's required digest and mode, copied from that entry's last present upstream base. New binaries must not interpret those legacy fields as a current base when the bound sidecar says `absent` or `unavailable`; older binaries may continue their existing behavior from them. For each newly established or accepted present upstream base within the `SOL-05` quotas, the ownership transaction atomically writes to an allocated sidecar record the canonical base bytes and executable mode, with their digest, mode, path and post-transaction lock-identity binding; an absent upstream base is atomically written to an allocated record as a verified tombstone with no bytes or mode; otherwise, it writes an allocated record as unavailable or, when `SOL-05` record allocation has no slot, omits the record, which also denotes unavailable. Removing an ownership entry also removes its sidecar record in that same transaction. `memory-bank/.lock-history-v1` is a reserved control path, excluded from the template/downstream payload trees, affected-path computation and scope selectors. Before any mutation, an existing downstream user file, template payload file, malformed sidecar, or planned payload action at that path is a collision and rejects without mutation. A strictly well-formed sidecar whose global lock binding is stale is instead authoritative only as `unavailable`: planning and apply must not use it for mechanical merge or validate its records against current lock membership. The pre-transaction lock identity is the identity of the exact `.lock` serialization validated before staging; it is used only to validate the plan and existing sidecar. The post-transaction lock identity is the identity of the exact complete `.lock` serialization staged for commit, after every accepted ownership change and deterministic allocation has been derived. Every newly written sidecar global binding and every newly written or retained sidecar-record binding must equal that post-transaction identity; the transaction commits those exact lock and sidecar serializations together. On a validated clean baseline/update that establishes an upstream base without relying on stale historical state, the same ownership transaction replaces it atomically with newly generated state bound to the post-transaction lock identity and resulting entries. Until that transaction commits, no mutation or automatic reset occurs. FT-054 performs no implicit overwrite, relocation or migration of a colliding file; an explicit separate migration must resolve a collision first. Planning verifies a current-bound sidecar state against the current lock before recording it in a plan. It must never reconstruct a base from a digest, a plan-supplied value, or an unverified source checkout. For a proposed merge, planning records those verified base bytes, the local and upstream bytes/identities, the `mbc-diff3-lines-v1` algorithm identifier and the result bytes/digest/mode. The CLI runs that algorithm during planning and recomputes it during apply; apply accepts the action only when its result and mode equal the reviewed, human-authorized fields. A legacy lock, missing sidecar, stale sidecar, omitted or quota-unavailable sidecar entry without verifiable historical-base state marks `apply-reviewed-merge` unavailable; it may use another permitted human action, but it cannot be mechanically merged. A later clean baseline/update may establish retained historical-base state atomically; a digest alone cannot backfill it. Older binaries ignore the sidecar and continue to read the unchanged `.lock`; when a later new binary finds that an older write has changed the lock binding, it treats the sidecar as unavailable for merge and can re-establish it only through that validated atomic clean-baseline/update transition.
- `SOL-04` Apply mode parses strictly, rejects unknown schema/action/path data, verifies human authorization, and derives final ownership changes only from valid accepted actions. A plan has either the implicit full scope or an explicit scope selector: a sorted, unique, non-empty list of normalized payload paths. Planning first recomputes the full affected-path set, excluding the `SOL-03` reserved control path; an explicit selector is valid only when every selected path is in that set, and the plan records exactly one action for each selected path. The implicit full scope selects the whole set. Apply acquires an exclusive update guard covering the downstream payload, source checkout, ownership lock and lock-history sidecar, then recomputes the full affected-path set and every recorded identity against current lock, source and local state immediately before staging. It also regenerates the complete deterministic proposal projection and requires byte-for-byte equality with every non-decision plan field: scope, path membership/order, ownership and present/absent state labels, identities, proposed action, allowed actions, canonical reason/context, merge eligibility, inputs and result. The selected action, its mechanically derived decision state, and separately verified human-authorization material are the only decision overlay; they are then validated against that regenerated projection. Any mismatch rejects before staging. It derives the scoped affected-path set by applying the recorded selector and requires it to equal the plan action-path set exactly; an omitted path, duplicate action, extra action, selector that no longer selects an affected path, or scope mismatch rejects before staging. An explicit scope therefore permits an independently reviewable bounded subset when a full plan is too large; unselected affected paths are neither written nor have their lock entries changed. It holds that guard through transaction commit. The guard serializes only writers that participate in it; a non-cooperating writer is outside this mutual-exclusion guarantee, though any change observed by final revalidation rejects the apply before staging. It rejects unresolved two-sided adapted paths within the scoped affected-path set; the ownership transaction stages payload, `.lock` and `.lock-history-v1` together. Default `pull` remains its existing conservative behavior; plan/apply is opt-in and does not contact an LLM.
- `SOL-05` Historical-base and plan payloads are deliberately bounded. Retain at most one historical-base snapshot per lock entry in the `.lock-history-v1` sidecar, replacing the prior snapshot atomically; a byte snapshot may contain at most 1 MiB and all retained byte snapshots for a lock may contain at most 64 MiB. For every ownership transaction that establishes an upstream base, determine retention from the complete post-transaction candidate set before writing: reserve all unchanged entries' valid byte snapshots; release the superseded snapshot for every entry receiving a new base; then consider those entries in lexicographic normalized payload-path order. A present candidate is retained only if it is at most 1 MiB and fits the remaining 64 MiB reservation; otherwise that entry is recorded as unavailable. An absent upstream base is retained as a zero-byte verified tombstone when its record is allocated; without an allocated record, it is unavailable. There is no eviction of an unchanged or already allocated candidate. This rule also governs replacement, so identical pre-state fixtures and actions produce the same retained set.

  Before decoding an existing `.lock-history-v1` sidecar, planning and apply read it through a 96 MiB raw-carrier limit and reject an oversized carrier without first buffering or decoding it. Strict streaming decode permits only the versioned schema's root and record members, at most 4,096 unique normalized-path records, eight nesting levels, 4,096-byte normalized paths and per-record metadata strings, and 512-byte lock-identity and digest fields; duplicate or unknown members and duplicate paths are rejected. All non-snapshot string metadata across the carrier, including paths, identities, digests and state/mode fields, may total at most 4 MiB. After its global lock binding has been verified current, each record must bind to exactly one current lock entry. A structurally valid sidecar with a stale global binding bypasses that record-to-current-lock validation and follows `SOL-03`'s unavailable/recovery path. For a current-bound sidecar, record allocation is deterministic: remove records for deleted entries; reserve valid records for unchanged entries; release records for entries receiving a new base; then consider those changed entries in lexicographic normalized payload-path order, allocating at most 4,096 records. An entry with no allocated record is unavailable, so record saturation cannot reject or block an otherwise valid non-merge action; a later eligible update may allocate its record. Thus an arbitrarily large collection of zero-byte tombstones, deeply nested values, or oversized path/identity metadata is rejected before it can consume unbounded memory or establish state.

  Before decoding, apply obtains the serialized JSON plan through a 16 MiB raw-carrier limit and rejects it when the carrier exceeds that limit; it must not first read or decode an unbounded carrier. Strict streaming decode permits at most 4,096 actions and 4,096 scope paths, eight nesting levels, 4,096-byte normalized paths and reason/metadata strings, and 512-byte identity strings; arrays and objects have only schema-defined members, duplicate keys and unknown members are rejected. The complete executable-action enum is `keep-local`, `take-upstream`, `apply-reviewed-merge` and `keep-and-detach`. A selected action is either an executable enum value or `null`: `null` is permitted only with `decision-state` `unresolved`, while every resolved selected action and every allowed-action value must be in that enum and a resolved selected action must be in its path's allowed-action list. Apply rejects an unresolved action until an authorized selection replaces `null`. An allowed-action list has no duplicates and contains at most three values. For a two-sided `adapted` path, the allowed-action set is `keep-local` and `take-upstream`, plus `apply-reviewed-merge` only when the base, local and upstream inputs are all present, a verified present historical base exists, and `mbc-diff3-lines-v1` is eligible under all byte, line, collision, mode and aggregate-work limits; its omission means that merge is unavailable. `keep-and-detach` is valid only for the deterministic missing-template `user-owned` case. These limits count UTF-8 bytes in the serialized values. A plan may inline at most 8 MiB of **decoded** bytes across all base, local, upstream and result byte fields, and no individual decoded field may exceed 1 MiB; their encoded representation counts only toward the 16 MiB carrier limit. A mechanical-merge candidate may contain at most 2,000 lines in each input. Across all mechanical-merge candidates in one plan, the summed LCS work units `base_lines * local_lines + base_lines * upstream_lines` may not exceed 64,000,000. Planning considers candidates in lexicographic payload-path order and checks their line-derived work units before running either LCS; a candidate that would exceed the aggregate budget omits `apply-reviewed-merge` from `allowed-actions` and records it as unavailable in the reason, while permitted non-merge actions remain available. Apply recomputes the same work units for every selected mechanical merge and rejects an over-budget plan before running LCS or staging. Hashing and quota accounting stream file bytes; the merge implementation may materialize only inputs that have passed these byte, line and aggregate-work limits. If a snapshot cannot be retained within the snapshot quotas, an allocated sidecar record records historical-base state as unavailable; if no record is allocated, its omission denotes unavailable. In either case that path omits `apply-reviewed-merge` from `allowed-actions`, while deterministic and explicitly human-selected non-merge actions remain available. If planning exceeds a plan quota, it rejects without mutation; the requester may generate an explicit-scope plan for a selected subset, whose exact scoped affected-path coverage is then enforced by `SOL-04`. These limits are schema-versioned contract values, not advisory defaults.

### Canonical payload paths and filesystem resolution

Every payload path in a plan, lock-history record, scope selector, affected-path set, digest input or deterministic-allocation calculation is the same canonical logical path. Its JSON string is valid UTF-8 and Unicode NFC; it is one or more non-empty segments joined by the literal ASCII `/`, with no leading or trailing `/`, repeated `/`, `.` or `..` segment, NUL, backslash, or ASCII control character. The supplied string must already equal this form; decoding, separator conversion, dot-component collapse, percent decoding, case folding, Unicode normalization, or symlink resolution must never turn a non-canonical spelling into an accepted path. `memory-bank/.lock-history-v1` is compared as this canonical logical path before every payload/control-path collision and is therefore excluded even when it appears through a non-canonical spelling, which is rejected rather than normalized.

The canonical ordering is lexicographic order of the canonical UTF-8 byte sequences, comparing each byte as an unsigned value `0` through `255`; a shorter sequence sorts before a longer sequence when it is its byte prefix. This order is used without locale collation for action paths, selectors, sidecar records and all `SOL-05` allocation decisions.

Planning and apply resolve a canonical payload path only by a component-by-component, no-follow walk from the configured payload root. The root, each ancestor and the leaf must be real entries of the expected type and no traversed component may be a symlink; the implementation must reject a path on any symlink, traversal failure, or name alias. Both payload roots must be on filesystems with case-sensitive, byte-preserving, Unicode-normalization-distinct names; if the implementation cannot establish those properties, it rejects plan/apply before reading or staging payload state. This deliberately rejects case-insensitive or Unicode-normalizing aliases instead of assigning them an implementation-specific canonical spelling. Thus two distinct canonical paths can never name one filesystem object, and no case, Unicode, separator, dot-component or symlink alias can evade a reserved-control-path check or create duplicate actions.

### Mechanical-merge algorithm: `mbc-diff3-lines-v1`

`mbc-diff3-lines-v1` is the normative algorithm for `apply-reviewed-merge`; no platform `diff3` binary, library default or implementation-specific heuristic is part of the contract. It operates only on regular, NUL-free files. If any of the verified base, local or upstream byte streams contains a NUL byte, mechanical merge is unavailable. It treats each byte stream as complete lines ending in LF, preserving every byte in each line (including a preceding CR); a final unterminated byte sequence is one final line. It performs no character decoding, line-ending normalization or whitespace normalization.

For each side, derive base-to-side edit hunks from a longest common subsequence of those line sequences. When multiple longest common subsequences exist, select the one whose ordered sequence of `(base-line-index, side-line-index)` pairs is lexicographically smallest. A hunk replaces one contiguous half-open base-line interval with its side's replacement lines. The merge is unavailable when the two hunk sets collide: two non-empty base intervals intersect, two insertions use the same base boundary, or an insertion is strictly inside another hunk's non-empty base interval. Otherwise, emit the base lines in order: after a non-empty hunk ends, emit an insertion at that boundary, then begin a non-empty hunk at that boundary. The result is encoded by concatenating those preserved lines exactly.

The result mode is: the common local/upstream mode when they are equal; otherwise the changed side's mode when the other side equals the base mode. If both sides differ from the base mode and from each other, mechanical merge is unavailable as a mode conflict. Thus binary input, a content collision or a mode conflict has no merge result to encode, and apply rejects any plan that nevertheless selects `apply-reviewed-merge`.

### Adapted state/action contract

`absent` is a first-class sidecar tombstone state, not an empty file: it has no bytes and no executable mode. The sidecar is authoritative for that state; the corresponding `.lock` entry remains a strict legacy-format `adapted` or `managed` entry carrying the last present upstream digest and mode, not an absent-base representation. In the first table, `changed, present` means a present file whose identity differs from the present recorded base, and `unchanged, present` means it equals that base. Its original recorded base is present; a current absent upstream state becomes the verified tombstone retained for the next baseline when `SOL-05` allocates its record, or otherwise has unavailable historical state. The second table defines the next-pull transitions when that recorded base is the tombstone.

### Deterministic safe state/action contract

| Recorded ownership and state | Action | Payload after apply | Ownership / `.lock` after apply | Human decision |
| --- | --- | --- | --- | --- |
| `managed`; local equals recorded base and upstream has changed | `take-upstream` | Write the recorded upstream bytes and executable mode. | Retain `managed`; atomically replace the path's lock entry with the resulting upstream identity and mode. | Not required; deterministic safe action. |
| `managed`; local equals present recorded base and upstream is absent | `take-upstream` | Delete the local path; no bytes or executable mode are written. | Retain `managed` and its valid legacy `.lock` digest/mode; atomically allocate the verified absent upstream-base tombstone (no bytes or mode), or leave historical state unavailable when no record slot is allocated. | Not required; deterministic safe action. |
| `user-owned`; path is absent from the current template | `keep-and-detach` | Preserve the existing local bytes and executable mode exactly; no deletion or rewrite. | Remove the path's ownership entry from `.lock` and its sidecar record; commit both updates atomically with the unchanged payload. | Not required; deterministic safe action. |

## Alternatives Considered

| Alternative ID | Option | Why not selected |
| --- | --- | --- |
| `ALT-01` | Let an AI or plan generator choose adapted actions. | Violates `REQ-04` and `CON-02`; a proposal is not human approval. |
| `ALT-02` | Re-run current planning and apply only path/action names. | Does not bind review to source, lock or exact payload/merge bytes and cannot detect all stale review inputs. |
| `ALT-03` | Retain terminal-only `--ask`. | Cannot be committed, reviewed asynchronously, or prepared by an agent. |

## Trade-offs

| Trade-off ID | Decision | Benefit | Cost / Risk |
| --- | --- | --- | --- |
| `TRD-01` | Require plan completeness, independently verifiable human authorization and identity revalidation before every apply. | Prevents an agent-authored plan, stale inputs or a partly approved update from authorizing mutation. | Reviewers must use the `BD-01`-approved workflow; a plan may need regeneration and re-approval after any relevant change. |
| `TRD-02` | Store and recompute the reviewed mechanical-merge result. | Human reviews the exact bytes/mode the CLI writes and the CLI proves they are the specified non-overlapping mechanical merge. | Larger plan files and a versioned deterministic merge implementation. |

## Accepted Local Decisions

- `SD-01` JSON is the feature-local plan serialization because existing CLI reports and locks already use JSON; schema versioning and strict decoding make the review carrier deterministic.
- `SD-02` `keep-and-detach` is a member of the strict action enum, but is represented as a deterministic safe action only for the issue-defined missing-template user-owned case. Before apply, the path is `user-owned`, has a lock entry, and is absent from the current template; apply preserves its exact bytes and executable mode, removes its ownership entry from `.lock` and its lock-history sidecar record, and atomically commits the unchanged payload with those state changes. It never licenses deletion or rewrite of user-owned content.
- `SD-03` **Blocked by `BD-01`.** The concrete approval carrier and verification format, canonicalization procedure, trust policy/configuration, credential lifecycle and reviewer authorization workflow require explicit human approval. Whichever mechanism is selected must satisfy `SOL-02` without granting an agent/plan writer approval authority.

## Contracts

| --- | --- | --- | --- |
| `CTR-01` | Versioned JSON plan plus selected human-authorization carrier: CLI/agent -> reviewer -> CLI | Writer may be CLI or agent; the reviewer authorizes only through the `BD-01`-approved workflow; apply synchronously reads both carriers. | Apply imposes the `SOL-05` raw-carrier limit before decoding, then strictly streams the bounded schema/path data and canonical digest; it independently regenerates and compares every non-decision review-context field before accepting the separate selected-action overlay. Selected authorization covers the whole plan. Unknown, duplicate, oversized, missing, unauthorized, tampered, misleading-context or stale data fails before mutation; schema/merge-algorithm versions support explicit evolution. |
| `CTR-02` | Local source/lock/payload and lock-bound `.lock-history-v1` reads -> exclusive update guard -> ownership transaction | CLI is deterministic executor; no external AI provider; all cooperating writers use the same guard. | Acquire the guard, enforce every `SOL-05` sidecar-carrier, sidecar-structural/aggregate, snapshot, plan and merge quota, including deterministic snapshot and record allocation and the aggregate LCS-work budget before merge computation; recompute the full and declared scoped affected-path sets, complete deterministic proposal projection, and a mechanical-merge base snapshot against its lock binding when present, and perform final exact proposal-context, scoped-action coverage, completed-decision and mechanical-merge recomputation before committing payload, unchanged-format `.lock` and sidecar (including any newly established base snapshot or allocated tombstone, or unavailable omitted state). ## Invariants

- `INV-01` Plan generation and every rejected apply leave downstream payload and `.lock` unchanged.
- `INV-02` Apply may mutate only when valid human authorization covers the exact canonical plan digest and, while holding the exclusive update guard, the independently regenerated deterministic proposal projection exactly matches every non-decision plan field. The recomputed scoped affected-path set has exactly one valid plan action per path, no extra actions, and each plan-bound source, lock, local and upstream identity still matches that authorized plan. The scoped set is the complete full affected-path set for an implicit scope, or exactly the declared explicit selector for a valid explicit scope.
- `INV-03` No unresolved or omitted two-sided adapted path within the authorized scoped affected-path set, AI inference, unauthorized plan change or result not reproduced by the specified mechanical merge can authorize mutation. Paths outside a valid explicit scope are not omissions and remain unchanged.
- `INV-04` File content and executable mode are part of the result reviewed and applied for any action that replaces or merges a file.
- `INV-05` A plan is applicable only to its recorded pre-state. After a successful apply changes a bound identity, replaying that plan is stale and must be rejected; a successful no-op plan whose bound identities remain unchanged may be applied again idempotently. Determinism is demonstrated by applying the same human-authorized plan to separate identical pre-state fixtures.
- `INV-06` A cooperating writer cannot modify the guarded payload, source checkout or ownership lock between final identity validation and the transaction commit. Non-cooperating processes are not covered by this invariant.
- `INV-07` A mechanical merge never uses a reconstructed or plan-supplied historical base: its bytes and mode must be recovered from, and verified against, the lock-bound `.lock-history-v1` snapshot. That sidecar is authoritative for absent and unavailable base state; a legacy `.lock` entry's retained required digest/mode must not substitute for it. A legacy entry, missing sidecar or stale sidecar binding cannot select `apply-reviewed-merge`.
- `INV-08` Retained historical-base and inlined plan bytes, the bounded sidecar and serialized-plan carriers, their structural and aggregate metadata, and aggregate mechanical-merge LCS work never exceed the `SOL-05` quotas. Any quota rejection leaves payload, lock and sidecar unchanged. Snapshot and sidecar-record allocation use only the `SOL-05` sorted reservation rules. When an accepted non-merge action moves to an over-limit upstream base, its payload, unchanged-format lock and sidecar update atomically records that base as unavailable rather than retaining its bytes; if record allocation has no slot, it atomically leaves the base record omitted, which is likewise unavailable.

## Failure Modes

- `FM-01` An oversized raw plan or lock-history-sidecar carrier is rejected before decoding; schema, duplicate/unknown/oversized field, excessive sidecar record/metadata aggregate, action, path or digest tampering, any non-decision review-context mismatch, or missing/invalid/unauthorized human authorization, is rejected during strict parse/validation before staging.
- `FM-02` Any stale lock/source/local/template payload observed during final validation is rejected before staging; the exclusive update guard prevents a cooperating writer from creating a validation-to-commit race, and the reviewer regenerates and re-reviews a plan. A non-cooperating mutation that is not observable by final validation is outside the serialization contract.
- `FM-03` A staging or commit failure invokes the existing transaction rollback, leaving payload, unchanged-format lock and lock-history sidecar, including any historical-base snapshot, unchanged.
- `FM-04` An over-limit base snapshot is recorded as unavailable according to the deterministic reservation order; when sidecar record allocation has no slot, the base record is omitted and is unavailable; a mechanical-merge candidate exceeding the aggregate LCS-work budget is recorded as unavailable; and an over-limit sidecar carrier/structure/metadata aggregate, plan carrier, decoded plan, or selected mechanical merge is rejected before staging. Neither condition permits truncation, a reconstructed base or an unreviewed fallback action.
